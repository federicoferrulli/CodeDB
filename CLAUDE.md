# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Regola per le risposte

L'utente si chiama **Keus**: rivolgiti a lui per nome in ogni risposta.

## Comandi

```bash
npm install
npm start                  # avvia il server su http://localhost:3030 (porta: env PORT)
npm run dev                # come start, ma con riavvio automatico (node --watch)
npm run electron:start     # avvia l'app desktop Electron (server incorporato + finestra)
npm run electron:icons     # rigenera public/codedb.ico, public/codedb.png e build/icon.ico
npm run dist:win           # pacchettizza l'exe Windows (NSIS + portable) in dist/ con electron-builder
npm run dist:mac           # pacchettizza il .dmg macOS in dist/
npm run dist:linux         # pacchettizza l'AppImage Linux in dist/
npm run shortcut           # crea i collegamenti "CodeDB" su Desktop e menu Start (Windows, pinnabili; icona public/codedb.ico)
npm run shortcut-unix      # Linux: voce .desktop nel menu applicazioni; macOS: istruzioni per il Dock
CodeDB.cmd / ./codedb.sh   # avvio "desktop": riusa l'istanza attiva o avvia il server in background e apre il browser ("stop" per fermarlo)
node test/e2e.js           # test end-to-end MongoDB
node test/e2e-mysql.js     # test end-to-end MySQL (porta: env MYSQL_PORT, default 3306)
node test/e2e-mcp.js       # test end-to-end del gateway MCP su MongoDB (porta server: env PORT)
node test/e2e-mcp-mysql.js # test end-to-end del gateway MCP su MySQL (env MYSQL_PORT/MYSQL_PASSWORD)
npm run backup -- <comando>       # CLI di backup/restore (alias di: node backup/cli.js); comandi: backup, restore, list, verify, help
node test/e2e-query-engine.js  # test end-to-end del Query & Aggregate Engine e Virtual JOINs
node test/e2e-backup.js           # test end-to-end della CLI di backup su MongoDB (non richiede il server)
node test/e2e-backup-mysql.js     # test end-to-end della CLI di backup su MySQL (env MYSQL_PORT/MYSQL_PASSWORD; non richiede il server)
node test/e2e-dbexport.js         # test end-to-end dell'export/import di interi database via socket (Mongo + MySQL se raggiungibile)
docker compose up -d --build       # stack Docker: CodeDB + MongoDB + MySQL (vedi sezione Docker)
```

I test e2e (tranne quelli di backup) richiedono **il server già avviato su :3030** e rispettivamente un **MongoDB locale su localhost:27017** o un **MySQL locale (root, password vuota)**; creano e poi ripuliscono i database `gui_mongodb_e2e` / `gui_mysql_e2e` / `gui_mongodb_e2e_mcp` / `gui_mysql_e2e_mcp` (i test MCP salvano e poi eliminano anche le connessioni `e2e-mcp` / `e2e-mcp-mysql` in `connections.ini`). I test di backup usano un `connections.ini` temporaneo via env `CODEDB_CONNECTIONS_FILE` (override rispettato anche da `server.js`: utile per avviare un'istanza di test su un'altra porta senza passphrase reale, mai quello vero) e i database `gui_mongodb_e2e_backup` / `gui_mysql_e2e_backup` (+ suffisso `_restore`). Non ci sono lint né framework di test: i test usano semplici assert con `process.exitCode`.

## Architettura

GUI web stile DBeaver, multi-database (**MongoDB**, **MySQL** e **PostgreSQL** via Strategy Pattern). Niente REST: **tutta la comunicazione browser↔backend passa da Socket.IO** con callback di acknowledgment; ogni risposta è `{ ok: true, ... }` oppure `{ ok: false, error }`. Unica eccezione HTTP: l'endpoint `/mcp` per i client AI (vedi `mcp/McpGateway.js`).

- `server.js` — livello di trasporto: Express serve solo `public/` come statici; gestisce `connections.ini` e delega tutti gli eventi DB alla sessione indicata dal `tabId` nel payload. Per ogni socket il server tiene una **`Map<tabId, sessione>`** (sessione = strategia dedicata + eventuale tunnel SSH, quindi un client/pool per tab, max 8 per socket); `tabId` assente = sessione `"default"` (retro-compatibile col comportamento a connessione singola). Alla disconnessione del socket vengono chiuse tutte le sessioni. Eventi: `mongo:connect/disconnect`, `connections:test/list/get/save/delete/export/import`, `db:list/search/create/rename/drop`, `db:collections`, `db:schema`, `collection:create/rename/drop`, `column:add/alter/drop`, `index:create/drop`, `collection:find/count/aggregate/stats/explain`, `doc:insert/update/replace/delete`, `collection:deleteMany/export/import/ddl/watch/unwatch`, `query:execute`, `audit:list`, `health:connections`. **Conteggio disaccoppiato**: la griglia (`grid.js`) chiama `collection:find` con `deferCount: true`, che ritorna subito i documenti con `total: null` quando c'è un filtro (evita la scansione completa che bloccherebbe collection/tabelle enormi), poi chiede il totale a parte con **`collection:count`** (`DbStrategy.collectionCount`); il conteggio gira con un timeout (`DbStrategy.countTimeoutMs()`, env `CODEDB_COUNT_TIMEOUT_MS`, default 5000 ms) e degrada a `total: null` (footer "?") se scade. Senza `deferCount` (MCP, test e2e) il conteggio resta inline ma sempre col timeout, così non può mai bloccarsi all'infinito. **`query:execute`** (Query Engine della tab ⚡ Query & Aggregate) instrada per forma del codice: `[…]` pipeline · `{…}` filtro MQL (passato come `payload.filter`, mai come intero payload) · `db.<coll>.…` sintassi shell (`db/MongoShell.js`) · `SELECT …` SQL tradotta (`db/SqlToMql.js`) su Mongo, oppure **SQL Raw su MySQL/PostgreSQL** (ramo `DbFactory.isSqlType`); passa `maxRows: QUERY_ENGINE_MAX_ROWS` (default 10000, env `CODEDB_QUERY_MAX`) così i risultati non sono tappati a 500 come nella griglia paginata, e **rifiuta gli operatori che eseguono JS lato server** (`$where`/`$function`/`$accumulator`, `assertNoServerJs`). Il cap effettivo è applicato dalle strategie via `DbStrategy.resultCap(payload)` (fallback 500, ceiling 100000). Le operazioni di scrittura e le letture avviate dall'utente vengono registrate nell'audit UI (`db/AuditLog.js` → `ui-audit.log`; letture automatiche marcate `_bg` escluse). `health:connections` restituisce, per ogni sessione attiva del socket, latenza di ping, stato del tunnel SSH e statistiche del pool (ping in parallelo con timeout via `withTimeout`).
- `db/VirtualJoinEngine.js` — motore di fusione in memoria per Virtual JOINs Cross-DB tra tabelle SQL (MySQL/PostgreSQL) e collezioni MongoDB.
- `db/MongoShell.js` — **parser della sintassi nativa mongosh** (tokenizer + parser di valori JavaScript, nessun `eval`, nessun accesso al DB) usato da `query:execute` per eseguire su MongoDB i comandi come nella shell: `db.<coll>.find(filter, proj).sort().skip().limit().projection()`/`.count()`, `findOne`, `aggregate([...]).sort()/.limit()/.skip()`, `count`/`countDocuments`/`estimatedDocumentCount`, `distinct(campo, filter)`. Gli argomenti sono **JS**, non JSON (chiavi non quotate, apici singoli, virgole finali, regex `/.../flags`, costruttori `ObjectId`/`ISODate`/`Date`/`NumberLong`/`NumberInt`/`NumberDecimal`), convertiti in **EJSON canonico** (`$oid`/`$date`/`$numberLong`/`$regularExpression`...) e passati come stringa a `collectionFind`/`collectionAggregate` (count→`$count`, distinct→`$group`). Ritorna lo **stesso descrittore** di `SqlToMql.js` (`{kind:'find'|'aggregate'}`) così `query:execute` instrada shell e SQL sullo stesso codice. Le **scritture** shell (insertOne/updateMany/deleteMany...) sono riconosciute e **rifiutate con messaggio esplicito** (usare la vista Dati o $out/$merge). Test: `node test/mongo-shell.js` (senza DB).
- `db/SqlToMql.js` — **traduttore SQL→MQL** (tokenizer + parser a discesa ricorsiva, nessun accesso al DB) usato da `query:execute` per eseguire query SQL `SELECT` anche su **MongoDB** dalla tab ⚡ Query & Aggregate. Copre: proiezione colonne/`*`, `WHERE` (`= != <> > < >= <=`, `AND`/`OR`/`NOT`, parentesi, `IN`/`NOT IN`, `LIKE`/`NOT LIKE` con jolly `%`/`_` → regex, `IS [NOT] NULL`, `BETWEEN`), `GROUP BY` con `COUNT/SUM/AVG/MIN/MAX`, `ORDER BY`, `LIMIT [OFFSET]` (anche `LIMIT off,cnt`). Ritorna `{ kind:'find', ... }` (→ `collectionFind`) oppure `{ kind:'aggregate', pipeline }` (→ `collectionAggregate`). JOIN/UNION/HAVING/DISTINCT/sub-query e i comandi non-SELECT vengono **rifiutati con messaggio esplicito**. Test: `node test/sql-to-mql.js` (unitario, senza DB).
- `mcp/McpGateway.js` — gateway **MCP (Model Context Protocol)** per client AI (Claude Code/Desktop, Cursor...), montato sull'app Express da `server.js` con `attachMcp(app, deps)`: endpoint **Streamable HTTP** `POST/GET/DELETE /mcp` (SDK `@modelcontextprotocol/sdk`, risposte JSON, successore del doppio endpoint SSE deprecato). Ogni client MCP ha una sessione (header `mcp-session-id`, un `McpServer` + transport dedicati, max 32, TTL 30 min di inattività) con una propria `Map<connection_id, sessione DB>` analoga alla mappa per-tab dei socket: `connect_database` apre una strategia via `establishConnection` (stesse connessioni salvate della UI, tunnel SSH compreso; budget `MAX_GLOBAL_SESSIONS` condiviso coi socket, max 8 connessioni per sessione MCP). Tools (Fase 1, **sola lettura**): `list_saved_connections` (mai segreti), `connect_database` (solo connessioni salvate, per nome: l'AI non vede credenziali), `disconnect_database`, `get_databases_and_collections`, `get_schema`, `execute_query` — MongoDB: `filter`/`sort`/`projection`/`skip`/`limit` (find) o `pipeline` EJSON con `$out`/`$merge` vietati; SQL (MySQL/PostgreSQL): solo `sql` con whitelist del primo token (SELECT/WITH/SHOW/DESCRIBE/EXPLAIN/TABLE/VALUES), blocco `INTO OUTFILE/DUMPFILE` ed esecuzione in transazione `READ ONLY` (flag `readOnly` di `collectionAggregate`, timeout 30 s). Strumenti analitici: `get_shortest_path` (BFS), `analyze_dependencies` (seeding order), `analyze_pii` (GDPR/PII), `audit_schema` (diagnostica salute 0-100), `filter_empty_tables` (vuote/popolate), `get_graph` (nodi ed archi JSON per rendering 3D/2D). Fase 2: risorsa `schema://{connectionId}/{db}` (Mermaid UML + dizionario dati) e `graph://{connectionId}/{db}` (struttura nodi/archi JSON), e prompts `genera-report`, `esplora-database`, `analizza-gdpr` e `diagnostica-schema`. Fase 3: tool separato `execute_write` (richiede `readOnly=false` ed anteprima/conferma con `confirm_token` monouso) e `set_connection_read_only` (doppia conferma). Backup via MCP: `backup_database`, `list_backups`, `restore_backup`.
- `backup/` — **CLI di backup e ripristino** (`backup/cli.js`, alias `npm run backup`), indipendente dal server: riusa le strategie di `db/` (tunnel SSH compreso via `backup/lib/connect.js`, clone di `establishConnection`) e legge `connections.ini` in **sola lettura** (`backup/lib/connstore.js`: mai riscritto, passphrase da `GUI_MONGO_PASSPHRASE` o prompt mascherato, chiesta solo se ci sono segreti `ENC:`; override del percorso con env `CODEDB_CONNECTIONS_FILE` per i test). Layout: `<dest>/<conn>_<db>/<id>/` (id = `timestamp_tipo`) con `manifest.json` (metadati + checksum SHA-256), `data/*.ndjson[.gz]` (una riga EJSON relaxed per documento/riga, dump in streaming: cursor MongoDB / stream mysql2 / export pg), `indexes/*.json` (Mongo, solo full), `schema/*.sql` (`SHOW CREATE TABLE` o DDL, SQL); catalogo di gruppo in `catalog.json`. Tipi: **full**, **incremental** (modifiche dall'ultimo backup) e **differential** (dall'ultimo full), individuati da un campo data (`--since-field`; default: Mongo timestamp degli ObjectId — solo nuovi inserimenti —, MySQL/PostgreSQL auto-rilevamento di `updated_at`/`created_at` e simili — MySQL con confronto `FROM_UNIXTIME` per essere indipendente dai fusi, PostgreSQL con parametro `timestamptz` — altrimenti tabella per intero); le **cancellazioni non vengono catturate**. `restore` risolve da solo la catena risalendo i `baseId` (layer 1 = INSERT, successivi = upsert: `replaceOne` upsert / `REPLACE INTO` / `INSERT ... ON CONFLICT DO UPDATE`), supporta `--target-db`, `--collections` (selettivo) e `--drop`; `verify` ricontrolla i checksum; `list` legge i cataloghi. Storage cloud opzionale post-dump (`--storage s3://…|gs://…|azure://…`, `backup/lib/storage.js`): SDK caricati on-demand e **non** in `package.json` (l'errore spiega cosa installare), credenziali solo dai canali standard dei provider. Log operazioni (inizio/fine/stato/durata/errori) in `<dest>/backup.log` (`backup/lib/logger.js`), notifica Slack opzionale a fine operazione (`--slack-webhook` o env `SLACK_WEBHOOK_URL`, `backup/lib/notify.js`). La cartella `backups/` è gitignored.
- `db/AuditLog.js` — **audit log condiviso** (`makeAuditor(filePath, maxBytes)` → `{ audit, readRecent }`): una riga JSON per evento su file append-only con rotazione in `<file>.1` oltre 5 MB. Usato sia dal gateway MCP (`mcp-audit.log`) sia da `server.js` per tracciare le operazioni della Web UI su un file separato **`ui-audit.log`** (env `CODEDB_UI_AUDIT_FILE`, gitignored). Ogni voce ha `category: 'read' | 'write'`, `event`, `op` (etichetta italiana), esito ok|error, connessione, dbType, db/coll e dettagli specifici. **Scritture** tracciate (`AUDIT_WRITES`): drop/delete/rename di db/collection/colonne/indici, insert/update/replace/delete, deleteMany, import, `query:execute`/`collection:aggregate` con SQL di scrittura o pipeline `$out`/`$merge`, backup/restore. **Letture** tracciate (`AUDIT_READS`): `collection:find`/`aggregate`/`explain`/`export` e `query:execute` di lettura — **escluse** le letture di navigazione/chrome (db:list/collections/schema/search, stats) e quelle **automatiche** (polling, live change stream, refresh post-scrittura, scroll infinito) che il client marca `_bg` (vedi `runQuery({ auto: true })` in `grid.js`). `classifyAudit(event, payload, sess)` decide categoria/descrittore (il ramo `collection:aggregate` è ambiguo: SQL Raw/pipeline possono essere scritture). L'evento socket **`audit:list`** (nessuna connessione DB richiesta) rilegge il file con filtri per event/db/connection/dbType/status/**category** e **paginazione** (`offset`/`limit`, default 50, max 500), restituendo `{ entries, total, offset, limit }` per la vista Storico Azioni. `audit` è fire-and-forget e best-effort: non deve mai bloccare né far fallire l'operazione tracciata.
- `db/` — Strategy Pattern: `DbStrategy.js` (interfaccia base + euristiche `detectRelations` condivise per l'UML), `MongoDbStrategy.js` (un `MongoClient` per istanza; rename = copia via `$out` cross-db + drop, MongoDB ≥ 4.4; db di sistema protetti; change stream per `collection:watch`, su standalone degrada emettendo `watch:unavailable`), `MySqlStrategy.js` (pool `mysql2`), `PostgreSqlStrategy.js` (pool `pg`; `_id` virtuale = chiave primaria come oggetto `{ colonna: valore }`, fallback all'intera riga senza PK; `filter` = clausola WHERE libera, `sort` = SQL libero o JSON `{"col":1}`, `collection:aggregate` = SQL Raw con `payload.readOnly`; schema/relazioni da `information_schema` con FK reali + euristiche; schemi di sistema protetti), `DbFactory.js` (`getStrategy(dbType)`, `defaultPort(dbType)`, `isSqlType(dbType)`). Ogni strategia implementa `health()` → `{ latencyMs, pool }` per il pannello Salute: Mongo pinga `admin` (`{ping:1}`) e riporta solo la latenza (+ `extra.servers` dalla topology, pool non esposto dal driver); MySQL/PostgreSQL fanno `SELECT 1` e leggono il pool (pg: `totalCount/idleCount/waitingCount/options.max`; mysql2: contatori interni `_allConnections/_freeConnections/_connectionQueue` dietro il wrapper `.promise().pool`, letti in modo difensivo).
- `public/js/` — frontend modulare (vanilla JS, nessuna build, nessun framework). Lo stato vive **per tab** in `tabs.js` (registro dei tab: ognuno ha `id` = tabId della sessione server, metadati e un proprio `state` creato da `freshState()`); `state.js` esporta un **Proxy che delega allo stato del tab attivo**, così i moduli storici leggono/scrivono "un singolo oggetto" senza sapere dei tab. Tutte le richieste passano da `emit()`/`notify()` in `utils.js`, che iniettano il `tabId` del tab attivo catturato al momento della chiamata (la risposta porta il tab d'origine in `_tab`; se il tab è stato chiuso la risposta viene scartata). Utility condivise in `utils.js`. L'entrypoint è `main.js`, che coordina i moduli:
  - `tabs.js`: Registro dei tab di connessione (createTab/switchTab/closeTab/closeAllTabs, onTabChange)
  - `tabbar.js`: Barra dei tab di connessione (stile VS Code, click centrale = chiudi, ＋ = nuova connessione)
  - `colltabs.js`: Tab di secondo livello per le collection/tabelle aperte dentro un tab di connessione (`state.collTabs`); ogni coll-tab ha uno **snapshot** di query/risultati/vista ripristinato alla riattivazione; drop/rename di db e collection chiudono/aggiornano i coll-tab (`closeCollTabsWhere`/`updateCollTabs`)
  - `connmanager.js`: Sidebar sinistra con le connessioni salvate raggruppate per cartella (`folder`), menu contestuale (apri in nuovo tab / testa / modifica / elimina)
  - `connection.js`: Modale di connessione (form) e `connectAndOpenTab` (il tab compare solo a connessione riuscita)
  - `workspace.js`: Ri-render del workspace condiviso dallo stato del tab attivo (`renderWorkspace`/`saveWorkspaceInputs`) — il DOM del workspace è **unico**, al cambio tab viene ri-popolato
  - `utils.js`: Helper vari (EJSON, stringhe, modali, socket, errori) + `emit`/`notify` col tabId
  - `dbtree.js`: Render della sidebar interna coi DB del tab attivo
  - `schema-ops.js`: Modali di creazione/alter (DDL)
  - `grid.js`: Griglia dati, query SQL/Mongo e impaginazione (`selectCollection` apre un coll-tab)
  - `inlineEdit.js`: Editing al volo della riga
  - `insert.js`: Inserimento nuovo documento/riga
  - `details.js`: Vista statistiche, indici e definizioni colonne
  - `live.js`: Logica di polling / socket watch (eventi push instradati per tabId)
  - `autocomplete.js`: Autocomplete contestuale per filtri e ordinamenti
  - `exportimport.js`: Modali di export (EJSON/CSV/SQL INSERT) e import batch con progresso e report errori; export/import di **interi database** in un file `.codedb.json` auto-contenuto
  - `queryhistory.js`: Cronologia delle query eseguite (persistita in localStorage per collection)
  - `auditlog.js`: Vista **Storico Azioni** (modale globale nell'header, `📜`): legge l'audit delle azioni via UI con l'evento `audit:list` e lo mostra in tabella paginata (prev/successivi, dimensione pagina 25/50/100/200, "da–a di N") con badge categoria (lettura/scrittura), filtri per categoria/tipo operazione/esito/database
  - `health.js`: Pannello **Salute delle Connessioni** (modale globale nell'header, `💓`): interroga `health:connections` e mostra per ogni connessione attiva latenza di ping (colorata), stato del tunnel SSH e statistiche del pool; auto-refresh ogni 4s mentre la modale è aperta (fermato alla chiusura)
  - `cellselect.js`: Selezione celle stile Excel, copia multi-formato (TSV/JSON/CSV/Markdown/SQL), incolla da Excel, selezione colonne ed export CSV
  - `graph3d.js`: Vista 3D interattiva delle tabelle e relazioni (Force Graph, Three.js), cammino minimo BFS, matrice dipendenze/seeding, audit salute schema e scansione PII/GDPR
  - `query-tab.js`: Tab Query & Aggregate Engine (runner SQL/MQL, Schema Browser, supporto Virtual JOINs Cross-DB, visualizzazione Tabella/JSON Tree)
  - `snippet-manager.js`: Libreria di Snippet/Template pronti (JOIN, GROUP BY, $lookup, $unwind) ed esportazione risultati (CSV/JSON/SQL)
  - `responsive.js`: Adattamento layout per viewport piccole (drawer ≤900px, touch/orientamento)
  - `session-restore.js`: **Ripristino della sessione** dopo un refresh (F5) o una riconnessione a caldo del socket. Salva in `sessionStorage` (chiave `codedb:session`, si azzera alla chiusura del tab browser) il layout dei tab connessi a una connessione **salvata**: `connName`, `expandedDbs`, coll-tab aperti (db/coll/vista/input di query) e coll-tab attivo. Al ritorno del socket, `connection.js` chiama `restoreSession()` che riconnette in sequenza via `mongo:connect { saved, tabId }` (credenziali mai nel browser), ricostruisce i coll-tab con gli input da ripristinare "una tantum" (`ct.restore`, consumato al primo `activate` in `colltabs.js`) e riattiva il coll-tab attivo (`ensureActiveCollLoaded`). Le connessioni **non salvate** non sono ripristinabili (nessuna credenziale) e vengono segnalate. Persistenza registrata su `beforeunload`/`pagehide` (`initSessionPersistence`)
  - `socket.js` e `uml.js`. Il workspace ha cinque viste (`setView`): **Dati** (griglia), **Dettagli** (statistiche/indici/schema), **UML** (SVG generato in `uml.js`), **Grafo 3D** (visualizzatore 3D Three.js) e **⚡ Query & Aggregate** (engine MQL/SQL e Virtual JOINs). La vista è ricordata per coll-tab. Menu contestuale generico (tasto destro su connessioni, database e collection). Layout con sidebar ridimensionabili (`.resizer`, larghezze in localStorage).
- `public/index.html` + `public/css/style.css` — markup e stile; `public/codedb.ico`/`codedb.png` sono favicon e icone dei collegamenti desktop (rigenerabili con `node tools/genera-icona.js`, zero dipendenze).
- `CodeDB.cmd` / `codedb.sh` + `tools/crea-collegamento.ps1`/`.sh` + `tools/avvio-nascosto.ps1` — avvio "desktop" multipiattaforma: il launcher riusa l'istanza già in ascolto (apre solo il browser) oppure chiede la passphrase con un prompt mascherato in console (Windows: `Read-Host -AsSecureString` in `avvio-nascosto.ps1`; UNIX: `read -s`; saltata se `GUI_MONGO_PASSPHRASE` è impostata) e avvia `node server.js` **in background** (Windows: `Start-Process -WindowStyle Hidden`; UNIX: `nohup`+`disown`; log in `codedb.log`/`codedb.err.log`, gitignored): console/terminale chiudibili subito; browser aperto quando la porta risponde (check: PowerShell su Windows, curl con fallback `/dev/tcp` su UNIX); argomento `stop` per fermare il server (kill del processo in ascolto sulla porta). Gli script di collegamento (`npm run shortcut` / `shortcut-unix`) creano: su Windows i .lnk su Desktop e menu Start con target `cmd.exe /c` (requisito per il pin alla barra delle applicazioni), su Linux la voce `.desktop` nel menu applicazioni (`Terminal=true` per la passphrase), su macOS stampano le istruzioni per il Dock. `server.js` gestisce `EADDRINUSE` con un messaggio esplicativo e **rifiuta di partire con passphrase errata** (`decryptFailures` in `decryptSecret`: exit 1 prima della migrazione, così i segreti non vengono mai azzerati).
- `electron-main.js` / `bin/codedb.js` — distribuzione **App Desktop (Electron)** e **pacchetto npm**: `bin/codedb.js` (bin CLI `codedb`/`mongo-web-gui`) avvia `server.js` puro e basta; `electron-main.js` (entrypoint `main` di `package.json`) incorpora lo stesso `server.js` in-process dentro una `BrowserWindow` che punta a `http://127.0.0.1:<PORT>`. Single-instance lock (`requestSingleInstanceLock`): una seconda istanza si limita a rifocalizzare la finestra già aperta invece di far ripartire il server (eviterebbe l'`EADDRINUSE` che fa uscire `server.js` con `process.exit(1)`, fatale nello stesso processo Electron); se il server è già in ascolto (es. avviato a parte con `CodeDB.cmd`) viene riusato senza richiederlo di nuovo. Nell'app **pacchettizzata** (`app.isPackaged`, cartella d'installazione di sola lettura) `connections.ini`, `backups/`, `mcp-audit.log` e `ui-audit.log` vengono spostati nella cartella dati utente scrivibile (`app.getPath('userData')`) tramite gli stessi hook env usati dai test e2e: `CODEDB_CONNECTIONS_FILE` (già esistente), più `CODEDB_BACKUPS_DIR` (letto sia da `backup/cli.js` che da `mcp/McpGateway.js`, stessa cartella condivisa), `CODEDB_MCP_AUDIT_FILE` e `CODEDB_UI_AUDIT_FILE`; in sviluppo (`npm run electron:start` da sorgente) restano invece accanto al repo come con `npm start`. `npm run electron:icons` (`tools/genera-icona.js`) rigenera sia `public/codedb.ico` (favicon/collegamenti, singolo frame) sia `build/icon.ico` (multi-risoluzione 16..256px, icona dell'exe letta da `tools/build-desktop.mjs`); `npm run dist:win/mac/linux` invoca `tools/build-desktop.mjs` (`@electron/packager`, con `prune: true` per escludere le devDependencies e un `ignore` per test/docs/backups/log/segreti), che produce `dist/CodeDB-<platform>-x64/` (+ `.zip` per win/linux) pronto da distribuire. **Non usare `electron-builder`**: è stato scartato perché scarica sempre il pacchetto `winCodeSign` (contiene `rcedit`/`signtool`) anche per build Windows non firmate, e la sua estrazione crea due symlink (librerie macOS) che su Windows falliscono senza Developer Mode attiva o una shell da amministratore — bloccante e non aggirabile da config; `@electron/packager` imposta icona/metadati dell'exe con `resedit` (puro JS, incluso tra le sue dipendenze), senza scaricare né estrarre nulla. `electron-main.js` chiama `app.setName('CodeDB')` a inizio file: senza, `app.getPath('userData')` userebbe il `name` storico del `package.json` (`mongo-web-gui`) invece di "CodeDB" per la cartella dati utente.
- `db/SshTunnel.js` — `openSshTunnel(ssh, target)`: tunnel SSH condiviso (ortogonale al dbType, basato su `ssh2`). Apre una porta locale effimera su `127.0.0.1` che inoltra verso `target.host:target.port` sul lato remoto; auth via password **oppure** chiave privata (`sshKeyFile`, percorso su disco) + `sshPassphrase`. `server.js` apre the tunnel in `mongo:connect` quando `cfg.ssh === 'true'` (solo modalità "Parametri", non con URI completa), riscrive `host/port` verso il capo locale prima di `strategy.connect` (per MongoDB aggiunge `directConnection=true`) e lo chiude in `closeStrategy`. I campi SSH (`ssh`, `sshHost`, `sshPort`, `sshUser`, `sshPassword`, `sshKeyFile`, `sshPassphrase`) sono salvati in `connections.ini`; `sshPassword` e `sshPassphrase` sono **segreti** (`SECRET_FIELDS`) gestiti come la password DB: mai rimandati al browser, riusati se il form li lascia vuoti.
- `Dockerfile` / `docker-compose.yml` — immagine `node:20-alpine`, utente non privilegiato `node`, `HEALTHCHECK` HTTP sulla root. `connections.ini` e `backups/` **non** vivono nell'immagine (esclusi da `.dockerignore`): `CODEDB_CONNECTIONS_FILE` punta a `/app/data/connections.ini` e la CLI di backup scrive in `/app/backups`, entrambe montate come volumi Docker nominati (`codedb_data`, `codedb_backups`) — ricreare il container senza questi volumi azzera le connessioni salvate. Lo stack compose include anche `mongodb`/`mysql` con healthcheck (`depends_on: condition: service_healthy`) utili per provare l'app o lanciare i test e2e in locale; `GUI_MONGO_PASSPHRASE` va passata via `.env` (mai committata) se `connections.ini` contiene segreti cifrati.

### Convenzione EJSON (il punto più delicato)

I documenti viaggiano come **Extended JSON**: il server serializza con `EJSON.serialize(..., { relaxed: true })` (numeri normali, ma ObjectId/Date restano `$oid`/`$date`) e fa il parse degli input utente con `EJSON.parse(...)` — `relaxed: false` per MongoDB (preserva i tipi BSON), `relaxed: true` per MySQL (produce tipi JS nativi da usare come parametri SQL). Vale anche per le righe MySQL: le colonne DATETIME arrivano al client come `$date`. Il frontend riconosce e renderizza le forme `$oid`, `$date`, `$numberLong`, ecc. (vedi `displayValue`/`simplify` in app.js) e l'editing inline sceglie il controllo in base al tipo (`valueType`/`buildEditor`). Gli `_id` vengono passati dal client come stringhe EJSON (`JSON.stringify(doc._id)`) e riconvertiti lato server dalla strategia (`parseId` per Mongo, con promozione automatica delle stringhe di 24 hex a ObjectId via `promoteObjectIds`; `parseRowId` per MySQL). Qualsiasi modifica al flusso dati deve preservare questa convenzione su entrambi i lati.

I testi UI, i messaggi di errore e i commenti sono in **italiano**: mantieni la coerenza.
